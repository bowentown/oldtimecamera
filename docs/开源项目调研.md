## 0. 一页结论

1. **四个功能有一条共同暗线，但「书籍分享」是异类**：摄影 / 地点 / 笔记都是「此刻·此地·我」的第一人称瞬间，天然同属一条时间线；书籍是「公共目录里的外部实体 + 我的评价」，需要 ISBN、版本、封面、评分，心智和数据模型都不同。平铺成四个 Tab 会让产品变成一个相机 + 半个豆瓣 + 一个足迹 + 一个备忘录。
2. **最值得借鉴的不是某个 App，而是一个容器重构**：不做四个模块，做「一卷胶片」——每一格是一张照片，可挂地点、一段话、一本书；也允许「没有照片、只有一句话 / 一本书 / 一个地点」的空白格，用相纸底纹渲染成图。四个功能在零新增 Tab 的前提下全部存在。
3. **现成项目很多，但「可参考」≠「可复用」**：形态最像的一批（NeoDB、Immich、PhotoPrism、Dawarich、moodiary、Joplin、AppFlowy、KOReader、Pixelfed）几乎全是 AGPL/GPL，闭源商业 APK **一行代码都不能带**；真正能进产品的只有 MIT / Apache-2.0 / BSD 的少数项目（见 §3）。
4. **「分享」这两个字决定成本量级**：本地生成一张胶片风长图经系统分享面板发出 = 零后端 / 零账号 / 零审核；做成别人能看能评的 UGC = 账号 + 内容审核 + 备案 + 冷启动 + 举报处置，差两个数量级。
5. **国内做地点记录，合规先于技术**：底图只能用腾讯 / 高德 / 百度 / 天地图，坐标系用 GCJ-02；不要 Google Maps / Apple Maps / Mapbox / Leaflet+OSM 瓦片。建议只在拍照瞬间取一次位置，不做持续后台轨迹。

## 1. 先回答你：这四个功能凑一起怎么样

### 1.1 共同暗线与唯一异类

| 功能 | 记录对象 | 数据结构 | 内容从哪来 | 首次打开就有价值？ |
|---|---|---|---|---|
| 复古摄影 | 私有瞬间 | 图 + 时间 + 参数 | 用户拍 | ✅ 是 |
| 地点记录 | 私有瞬间 | 经纬度 + 地名 | 自动带出 | ✅ 依附照片 |
| 随心笔记 | 私有瞬间 | 一段文本 | 用户写 | ✅ 依附照片 |
| 书籍分享 | **公共目录实体** | ISBN / 版本 / 封面 / 评分 / 书评 | **外部元数据 + 他人内容** | ❌ 书库是空的 |

前三者共享同一行数据：`(occurred_at, location, media, text)`。第四者需要另建「作品 / 版本 / 作者」目录层，还需要外部数据源与内容供给。**这不是「加一个模块」，是加一条产品线。**

### 1.2 「分享」的歧义（这次最大的成本分叉）

- **A 义：导出**。端上把若干条目渲染成静态长图 / 卡片 / PDF，带自研水印，经系统 Share Sheet 发出。原始数据不出端。→ 后端 0、账号 0、审核 0、备案 0。
- **B 义：广播**。别人能在 App 里看到、点赞、评论。→ 账号体系、UGC 存储、文本 + 图片审核、举报与处置、未成年人保护、国内上架的 UGC 相关资质与备案（具体义务需法务确认）、冷启动内容供给与社交关系。

我的倾向：**V1 只做 A**，但在数据模型里预留 `visibility` 与 `external_ref`，将来要升级成 B 时不用改表。

### 1.3 我建议的重构：不做四个 Tab，做「一卷胶片」

```
胶片卷（唯一主界面，按 occurred_at 逆序／按胶卷分组）
  └─ 一格 = 一条 Entry
       ├─ 主体：照片（可为空）
       ├─ 固化：胶片型号 + LUT 参数 + 日期水印（拍照瞬间锁定，事后不可改）
       ├─ 自动附加：地点（一次定位，GCJ-02 + 地名）
       ├─ 可追加：随心笔记（一段话 / #标签）
       ├─ 可挂接：一本书（ISBN → 封面 / 短评 / 读到第几页）
       └─ 可见性：PRIVATE / SHARED_LINK（默认私有）
  └─ 无照片的格：用相纸底纹 + 排版渲染成图（一句话、一本书、一个地点都能成「一格」）
  └─ 出端产物：胶片风分享长图 / PDF / Markdown+媒体 ZIP（复用同一套渲染引擎）
```

好处：书籍、地点、笔记不再是「功能」，而是照片的**元数据层**；没有照片时它们自己也能成为一格，于是四个需求都满足，界面只有一个。数据层就是一张扁平 Entry 表 + `kind` 判别，而不是四套 CRUD。这个模型直接对应 `usememos/memos`（MIT）的 `memo + attachment + memo_relation + 内联 #tag + visibility + location`，也可参考 `neodb-social/neodb`（AGPL，只学思路）的「公共目录实体 / 用户私人记录」两层拆分。

### 1.4 Dazz Cam 真正值得学的是「约束」，不是滤镜

可免费借鉴的是思想与机制，不是资产：

- **可借鉴机制**：选胶卷 → 拍摄 → 不可撤销 → 限量张数 → 等待显影 → 归档；不同胶卷有不同颗粒 / 漏光 / 色偏；日期水印；「实时取景」与「延迟显影」并存。
- **可借鉴算法**：3D LUT 映射、双八度颗粒逐帧重播种、halation、暗角、褪色、曝光 / 白平衡。
- **不可照搬**：名称 / Logo / 拟物相机皮肤 / 图标 / 胶卷边框 / 颗粒漏光贴图 / 预设 LUT 数据文件 / 文案 / 示例图；不要使用胶片厂商商标作预设名；不要反编译或抠图。17 U.S.C. §102(b) 与 37 CFR §202.1 明确「思想、方法、操作方式、布局」不受版权保护，但**具体美术表达与数据文件可能受保护**。

**产品判断**：如果拍完还能随便换滤镜、无限重拍，它就只是个滤镜 App，不是胶片相机。「拍照即固化」这条约束反而让本地库、导出、备份、未来的同步全部变简单（不可变条目 + 只追加的元数据）。这是我认为最该从 Dazz Cam 拿走的东西。

### 1.5 冷启动

四个模块里，只有相机在用户第一次打开时就能产出一件「值得留下的东西」。书籍模块在书库为空、书评为空、社交关系为空时是死界面。所以相机必须是主入口，其余三者应作为「给已存在的照片补充上下文」出现，而不是并列入口。

### 2.5 聚合型 / 统一时间线

- `usememos/memos`（MIT）的「单一扁平条目 + payload + 附件 + 标签 + 地点 + 逐条可见性」是**最小充分模型**，也是唯一在许可证上可以放心参考的聚合型项目。
- `neodb-social/neodb`（AGPL）：把「可复用实体目录」与「用户私人记录」拆两层，正好对应「书籍/地点实体」与「胶片照片/笔记/评分」——只取思路。
- [pixelfed/pixelfed](https://github.com/pixelfed/pixelfed)（AGPL-3.0，7,141）、Mastodon（AGPL-3.0）：逐条可见性 / 联邦协议参考；**V1 不引入 ActivityPub**，它会把离线工具变成带公网 Actor 的社交产品，且生态参考实现全是 AGPL。
- 权限模型建议：`visibility ∈ {PRIVATE, SHARED_LINK, PUBLIC}` 逐条存储、默认 PRIVATE；分享只输出渲染产物，原始库与媒体不出端。

## 3. 决定生死的一层：闭源产品能碰哪些代码

你说喜欢「不开源」的 Dazz Cam，我按**闭源商业 APK** 这个前提来判。结论有点反直觉：**越像你产品的项目，越不能碰。**

6. **Capacitor 版本**：`ionic-team/capacitor` 的 `releases/latest` 实测是 **7.6.10**（2026-10-28）。你此前项目用的 Capacitor 8 未在官方仓库核实到正式 release，升级 / 复用前建议确认来源与插件兼容性。

## 4. 三条工程硬约束

### 4.1 相机链路必须落在原生层

实时取景每帧要做曝光 / 白平衡 → 3D LUT → 颗粒 / halation / 暗角，且全分辨率出图要走同一管线。WebView + Canvas 扛不住 30/60fps。若沿用你熟悉的 React 19 + TS + Vite + Tailwind v4 + Capacitor：

```
原生层（Kotlin）：CameraX 预览 → OpenGL ES / GPUPixel 渲染 → 固化出图 → Room/SQLite 落库
       ↑ Capacitor Plugin 桥（只传参数与结果，不传每帧像素）
JS 层（React）：胶片卷时间线、笔记/书籍/地点编辑、分享长图排版、设置
```

也就是说**栈可以留，但要接受混合架构 + 自研 Capacitor 插件**；纯 Web 方案不可行。参考实现正是 `FilmCamera-Android` 的 CameraX + OpenGL ES 管线。

### 4.2 一条 Entry 表，不要四张表

```
Entry(id, kind=PHOTO|NOTE|BOOK|PLACE, occurred_at, created_at, updated_at,
      deleted_at, revision, visibility, location_wgs84, place_name,
      film_preset, lut_params, date_stamp, text_md, book_isbn, mood,
      external_ref)
Attachment(id, entry_id, sha256, path, mime, width, height, is_primary)
EntryRelation(id, from_entry, to_entry, type)
Tag / EntryMeta(entry_id, k, v)      # #tag 内联，KV 承载类型差异
```

正文存 Markdown；媒体按内容寻址落在 app-private 目录；`uuid + 时间戳 + 软删除 + revision` 从第一天就预留，将来加同步零迁移；不申请 `INTERNET` 权限也能跑（书籍元数据查询做成可选、可关）。

### 4.3 国内地图合规（硬红线）

- **可用底图**：腾讯地图（未指定时默认）、高德、百度、天地图。
- **不可用**：Google Maps、Apple Maps、Bing 海外版、Mapbox、Leaflet + OpenStreetMap 瓦片、任何无资质第三方地图源。MapLibre 作为**渲染引擎**可用，但其瓦片源必须换成合规供应商。
- **坐标系**：GCJ-02；WGS-84 存储、渲染前用 `gcoord` 转换。
- **边界 / 领土表达**必须符合国家标准，不得错绘国界、台湾及南海诸岛；不得标注军事禁区等敏感坐标。
- **隐私**：个人打卡坐标只保留在本地私有存储；不得采集、存储或公开发布他人位置数据。批量点位数据须符合《个人信息保护法》。
- **Key**：不要在前端明文内置有效 key；需自行到对应开放平台申请，商业用途应通过后端代理鉴权并配置 Referer 白名单。

## 5. 我建议的 V1

> 一个**完全离线、无账号、无服务器**的 Android 胶片相机：拍一格 → 自动记下时间与地点 → 可补一句话 / 挂一本书 / 打个标签 → 按胶卷归档 → 一键生成胶片风分享长图或导出 Markdown+媒体 ZIP。

- 分享：端上渲染静态产物，系统 Share Sheet 发出；原始数据不出端。
- 存储：Room/SQLite（+ SQLCipher 待授权确认）、Android Keystore 管密钥。
- 不引入：账号、UGC 广播、ActivityPub、CRDT、AI 风格迁移、持续后台轨迹。

## 6. 想和你讨论的 7 个问题

1. **「分享」你指的是哪一种？** 我的倾向是「导出一张图」而不是「建一个社区」。如果你要的是后者，整个 §5 的 V1 都要重写，且合规预算要单列——这一条决定后面所有事。
2. **你愿意让照片「拍完就不能改滤镜」吗？** 我倾向「愿意」，因为这是 Dazz Cam 的灵魂，也是「旧时光」这个叙事的支点；但它会劝退一部分习惯先拍后修的用户。
3. **书籍模块可以接受「只有书目 + 一句短评 + 生成书单胶片」吗？** 还是你心里其实想要「能看到别人读什么」？前者零后端，后者是另一家公司。
4. **是否接受「相机原生 + UI 用 React/Capacitor」的混合架构？** 若坚持纯 Web，实时胶片预览基本做不出可用体验；若坚持全原生 Kotlin，你现有前端栈的复用率会很低。
5. **「复古」的边界在哪？** 只做滤镜与相纸，还是连「胶卷 24 张拍完才显影」「日期水印不可关」一起做？后者更有性格，但会明显降低日活。
6. **要不要从第一天就给书籍 / 地点数据留「外部实体目录层」？** 我的倾向是：V1 全部塞进 Entry 的可空字段，等书目去重真的痛了再抽表（NeoDB 的两层模型是成熟答案，但过早引入会拖慢 V1）。
7. **这个产品是给自己做的，还是要上架商业发行的？** 若只是自用 / 小范围，很多许可证与合规约束可以放宽；若确定闭源商业发行，§3 的依赖白名单就是硬约束，选型阶段就要锁死。

### v1.1.1 预览倒置与镜像 Bug 根因与修复架构
1. **根因**：`v1.1.1` 在 `GLFilmRenderer.buildTexMatrix()` 中把 `rotMatrix(rotationDegrees, mirror)` 左乘到 `SurfaceTexture.getTransformMatrix(stMatrix)` 之后（`rotMatrix * stMatrix`）。而绝大多数硬件 `CameraX` Preview 路径下 `TransformationInfo.hasCameraTransform() == true`，`stMatrix` 已内置传感器旋转、GL 纵向翻转与前置自拍镜像；叠加前置 `mirror + rotationDegrees` 导致屏幕 Y 轴翻转上下颠倒，且 `MainActivity` 初始硬编码 `90°` 亦忽略了 `cropRect` 与 `displayRotation`。
2. **修复**：抽离纯 Java 无 Android stub 依赖的 `CameraTransformMath`，严格区分 `hasCameraTransform == true`（仅补偿剩余显示旋转、用户校准与可选去镜像，右乘于 `stMatrix` 之前）与 `false`（显式组装 `cropRect -> rotate -> mirror` 再经 `stMatrix` 翻转），并通过 `isMatrixAxisSwapped(texMatrix)` 反推缓冲区宽高交换，确保各厂商 HAL 预览与成像 100% WYSIWYG。
3. **协同增强（低 UI 负担）**：极简暗房信息降噪（移除常驻文字简介与顶部冗长标题、缩短配置标签）、`OrientationEventListener` 真实横竖屏成像、`ExifInterface` 相机参数透传、`16:9` / `XPAN` 画幅、电子水平仪（暗房开关）、经典胶片双击翻转/左右滑切卷、前摄屏幕补光（`FLASH_MODE_ON`）与屏闪/Screen 混合双重曝光（`2×`）。
